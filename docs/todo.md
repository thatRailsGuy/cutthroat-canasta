## Web client

- [ ] Let players chat at the table. Today **Table talk** ([Feed.tsx](../apps/web/src/components/Feed.tsx)) lists only game events, and the protocol ([protocol.ts](../apps/server/src/protocol.ts)) has no message players can send to each other. Design with mockups: https://claude.ai/artifact/9ZGrpNk31H4z1sNE7w9zo6 (private, open it while signed in). **Decided:** chat is open in the lobby, the waiting room, and during play. A message has at most 200 characters, cleaned like join names. Each player can send 5 lines per 10 s, or the server answers `CHAT_TOO_FAST`. The room keeps the last 50 lines under its own storage key (`'chat'`, not inside `'room'`). On a phone, the **Scores** button shows an unread count. There is no moderation yet. **Planned design:** the client sends `{ type: 'chat', text }`. The server stamps a `ChatLine` (id, playerId, name, text, at, anchor) and announces `{ type: 'chat', line }` to every joined socket. It sends `{ type: 'chatLog', lines }` once after `joined`, so reconnects get the backlog. The anchor is `{ round, after: round.feed.length }`, so every client merges lines among the game events in the same place. Lines from the lobby or earlier rounds go first. The chat handling goes in [gameRoom.ts](../apps/server/src/gameRoom.ts) and a new `chat.ts`, because `handleMessage` in [room.ts](../apps/server/src/room.ts) has no clock. Lines are rendered as plain text in a `role="log"` list. **Still to confirm** (my picks in brackets): flip Table talk to oldest-first so a conversation reads top to bottom (yes). Waiting-room players can chat (yes). Show a desktop toast when Table talk is scrolled out of view (no). Later: quick reactions as preset chat text, a host mute, typing indicators.
